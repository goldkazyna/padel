# Americano Flex — дизайн режима

**Дата:** 2026-05-19
**Статус:** дизайн на ревью у пользователя, реализация не начата.

## 1. Зачем

В существующих турнирах Padel количество участников жёстко привязано к структуре кортов: классическое Американо требует кратное 4 (4, 8, 12, 16…). Если приходит, скажем, 10 или 11 человек на 2 корта — провести турнир в текущем формате нельзя. Кого-то приходится отправлять домой или искать запасного игрока.

Americano Flex решает эту проблему: режим запускает турнир для **любого** числа игроков `≥ M × 4 + 1` (где M — число кортов), формируя очередь и распределяя матчи так, чтобы каждый сыграл примерно одинаково.

## 2. Ключевые решения (после обсуждения с пользователем)

| Решение | Значение | Источник |
|---|---|---|
| Структура | Единый пул из N игроков на M кортов, **без групп и плей-офф** | PRD §1 + согласовано |
| Партнёры | Новые каждый раунд, по истории встреч | PRD §3 + согласовано |
| Длительность | Админ сам нажимает «Следующий раунд» / «Завершить турнир» | Согласовано (модель Король Корта) |
| Лидерборд | Чистое среднее `total_points / matches_played` | PRD §2 + согласовано |
| MVP scope | Базовая ротация + лидерборд + ELO по итогам. Без late entry / early exit / skip round | Согласовано |
| ELO | Через `RatingCalculator` trait, по каждому матчу — как в Mexicano | Архитектура проекта |

## 3. Алгоритм очереди

### Данные по каждому игроку (per-tournament)

- `matches_played` — сколько матчей в этом турнире сыграл
- `bye_streak` — сколько раундов **подряд** отдыхал (0 = играл в прошлом раунде)
- `bye_count` — сколько раз вообще отдыхал (для статистики)
- `total_points` — накопленные очки счёта

### Выбор игроков на следующий раунд

Нужно выбрать `M × 4` игроков из общего пула N. Сортируем по трём приоритетам:

1. **больше `bye_streak`** — кто дольше отдыхал, играет первым
2. **меньше `matches_played`** — кто меньше всего сыграл, играет следующим
3. **рандом** — при полном равенстве

После сортировки берём первые `M × 4` человек — это играющие. Остальные `N − M × 4` — отдыхающие.

### Алгоритм пар на раунд

На выбранных `M × 4` игроках формируем `M` матчей по 4 игрока (2 на 2). Используем готовую логику из `MexicanoService::generatePairsForRound()`:

- Минимизируем сумму `times_as_partners + times_as_opponents` для каждой потенциальной пары
- Если несколько вариантов с одинаковой суммой — берём рандом

История пар (`mexicano_pair_history` — переиспользуем как `americano_flex_pair_history` или общую таблицу) обновляется после каждого матча.

### Пример: 10 игроков, 2 корта, 4 раунда

| Раунд | Играют (8) | Отдыхают (2) | Кто заходит первым (priority 1) |
|---|---|---|---|
| 1 | P1, P2, P3, P4, P5, P6, P7, P8 | P9, P10 | — (рандом) |
| 2 | **P9, P10**, P1, P2, P3, P4, P5, P6 | P7, P8 | P9, P10 (bye_streak=1) |
| 3 | **P7, P8**, P9, P10, P1, P3, P5, P6 | P2, P4 | P7, P8 |
| 4 | **P2, P4**, P7, P8, P9, P10, P5, P6 | P1, P3 | P2, P4 |

Итог: каждый сыграл **3 или 4 матча** (разница ровно 1 = удовлетворяет Fairness Score из PRD §7).

### Конфликт правил: очередь vs уникальность пар

Иногда оптимальная пара невозможна — нужный партнёр «должен отдыхать» по очереди. **Очередь приоритетнее**: лучше пусть пара повторится, чем кто-то отдохнёт два раунда подряд.

Пример: P1 ещё не играл с P3 (была бы уникальная пара), но P3 имеет `bye_streak=1` — ему пора отдыхать. Алгоритм выбирает: P3 играет (справедливость), P1 берёт другого партнёра, **даже если был с ним раньше**. Это сознательный компромисс.

### Лимиты уникальности на длинных турнирах

Для N игроков всего возможных пар: `N × (N-1) / 2`. Например, для 10 игроков — **45 пар**. После исчерпания запаса пары начинают повторяться.

Таблица для 10 игроков на 2 кортах:

| Раундов | Матчей на игрока | Состояние пар |
|---|---|---|
| 5 | 4 | 20 уникальных пар, 0 повторов ✅ |
| 10 | 8 | 40 пар, 1–2 повтора |
| 11+ | 8+ | Повторы неизбежны |

**Sweet spot для 10/2: 5–10 раундов.** Алгоритм будет работать и дальше, но смысл турнира размывается.

### UI-подсказки админу про момент завершения

Когда `min(matches_played) == max(matches_played)` (все на равных):

> **«Каждый сыграл N матчей. Все игроки на равных — хороший момент завершить турнир.»**

Когда число уникальных пар приближается к `N × (N-1) / 2`:

> **⚠️ «Достигнут предел уникальных пар. Дальше партнёры начнут повторяться. Рекомендуется завершить турнир.»**

Без принудительных запретов — это nudge для админа, не блокировка.

## 4. Edge cases (решены явно)

### Минимум игроков

- 1 корт: минимум **5 игроков** (4 играют + 1 отдыхает).
- 2 корта: минимум **9 игроков**.
- Формально: `N ≥ M × 4 + 1`.

Если меньше — форма создания турнира **не разрешает** выбрать Flex, предлагает обычное Американо.

### Максимум игроков

PRD §6 рекомендует ≤ `M × 6` (1.5 игрока на место). Жёсткий лимит ставить не будем:

- При создании турнира — **warning** «У вас X игроков на Y кортов, многие будут долго ждать. Рекомендуется не более N».
- Турнир всё равно создастся, ответственность на админе клуба.

### `N = M × 4` (все играют, никто не отдыхает)

Технически Flex выродится в обычное Mexicano — алгоритм `bye_streak` будет всегда 0, останется только pair-history балансировка.

**Решение:** разрешаем (это удобно если игроки разъезжаются в процессе → в начале их было 11, потом стало 8). Никакой ошибки.

### Все игроки сыграли одинаковое число раундов на момент «Завершить»

Адмен нажал кнопку, у всех `matches_played` равны → проблем нет.

### Разное число матчей у разных игроков на момент «Завершить»

Это норма для Flex. Лидерборд использует чистое среднее → сравнение справедливо.

## 5. Хранилище

### Новый тип турнира

В `tournaments.type` добавляется значение **`americano_flex`** (миграция: `ALTER TABLE tournaments MODIFY type ENUM(..., 'americano_flex')`).

### Новые таблицы

```
americano_flex_rounds
  id, tournament_id, round_number, status (pending/in_progress/completed), created_at, updated_at

americano_flex_matches
  id, americano_flex_round_id, court_number,
  team1_player1_id, team1_player2_id, team2_player1_id, team2_player2_id,
  team1_score, team2_score, status, created_at, updated_at

americano_flex_byes
  id, americano_flex_round_id, user_id  -- кто отдыхал в этом раунде

americano_flex_players (pivot, аналог mexicano_players)
  id, tournament_id, user_id,
  total_points, matches_played, bye_count, bye_streak,
  rating_before, rating_after
```

Историю пар можно переиспользовать `mexicano_pair_history` (поменяв на нейтральное имя `tournament_pair_history` с полем `tournament_id`) — но это рефактор существующего кода, спорно. **MVP-решение:** добавить отдельную `americano_flex_pair_history` с той же структурой что и `mexicano_pair_history`. Дублирование, но изолировано.

### Почему отдельные таблицы, а не `mexicano_*`

- В `mexicano_matches` нет понятия «отдыхающих» — там все играют каждый раунд.
- Mexicano пересчитывает рейтинги между раундами (динамика), Flex — нет (рейтинг только в конце).
- Не мешаем существующему Mexicano, чтобы случайно его не сломать.

В Flutter — два экрана:
- **Играю**: «Корт 1 · Партнёр: Аня · Соперники: Сергей, Маша» + текущее место в таблице.

Никаких таймеров и «партнёр в следующем раунде» в MVP (PRD §5 — на v2).

## 8. Расчёт ELO

Как в Mexicano: каждый сыгранный матч даёт дельту через `RatingCalculator::calculateRatingChange()`. При нажатии «Завершить турнир»:

1. Идём по всем `americano_flex_matches` со `status=completed` в порядке создания.
2. Для каждого: считаем `change1`/`change2` для team1/team2.
3. Применяем к рейтингам игроков последовательно (current rating меняется по ходу).
4. Сохраняем `rating_before` (= начальный) и `rating_after` (= итоговый) в `americano_flex_players`.
5. Обновляем `users.rating` через стандартный механизм клуба.

Отдыхавшие в раунде — рейтинг не меняется в этом раунде, никаких штрафов.

## 9. Что НЕ делается в MVP

- Late entry — добавление игрока в середине турнира
- Early exit — вывод игрока с сохранением его результатов
- Skip round — админ-кнопка «Иван пьёт воду, исключить из следующего раунда»
- Таймер раунда в мобильном
- Показ «партнёр в следующем раунде» (невозможно знать заранее без преждевременной генерации)
- Push-уведомления типа «начался твой раунд»

Всё это — отдельные тикеты после MVP. Если в процессе появятся явные запросы — открываем v2.

## 10. Метрики готовности MVP

1. **Fairness:** разница `matches_played` между самым и наименее активным игроком ≤ 1 (тест на 5+ раундов).
2. **Никто не отдыхает дважды подряд** при `N ≤ M × 5` (математически возможно — проверим в тесте).
3. **Лидерборд** корректно сортируется по среднему.
4. **ELO** обновляется только при завершении турнира (`Завершить турнир`).
5. **Генерация следующего раунда** < 2 секунды (PRD §7) — это не должно быть проблемой при N < 30.

## 11. Открытые вопросы для пользователя

1. Действительно ли мобильное приложение должно показывать имена соперников и партнёра в текущем раунде, или достаточно номера корта? (PRD намекает на полный состав, но это влияет на payload.)
2. Что показывать в лидерборде помимо имени и среднего? Колонки: сумма очков, число матчей, рейтинг до→после — нужно всё?
3. Если игрок зарегистрирован в турнире, но не пришёл — он будет считаться «отдыхающим всегда» и портить статистику. Нужна ли в MVP кнопка «не пришёл» в админке (мягкий early exit)? Я по умолчанию отнёс это в v2, но если без неё совсем не запустимо — пересмотрим.
