# Достижения игрока

Дизайн от 16 августа 2026. Фишка релиза 1.8.0 мобильного приложения.

## Зачем

Игроки возвращаются в приложение, когда записываются на турнир, и пропадают между турнирами. Нужен повод открыть его в остальные дни и причина доиграть до цели.

Достижения выбраны из трёх вариантов (ещё рассматривались «досье на соперников» и «итоги месяца картинкой»), потому что непонятно, кто именно отваливается — новичок после первого турнира или регуляр в паузе. Достижения работают в обоих случаях: новичку значки падают сразу, регуляру остаются длинные цели. И это единственный из трёх вариантов, который сам стучится к ушедшему — пушем.

## Что получает игрок

**Свой профиль.** Блок «Достижения»: полученные значки цветные, ближайшие неполученные — тусклые с прогрессом («8 / 10 турниров»). Тап открывает экран со всеми значками, сгруппированными по разделам.

**Чужая карточка игрока.** Только полученные значки. Без пустых ячеек и без счётчика «3 из 15»: смотреть на чужие успехи приятно, видеть свою пустоту рядом — нет.

**Пуш при получении.** «Новое достижение: Серия». Тап ведёт на экран достижений. Отдельная категория уведомлений, чтобы игрок мог отключить только её.

Значки видны всем и общие для всей платформы: игрок собирает их в любом клубе, при смене клуба история не теряется.

## Набор значков

Пятнадцать штук в пяти группах. Формулировка прогресса у каждого — «сделано / нужно».

### Первые шаги
| Код | Название | Условие |
|---|---|---|
| `first_win` | Первая победа | выиграть первый матч |
| `debut` | Дебют | сыграть первый турнир |
| `regular_5` | Пятёрка | 5 турниров |
| `regular_10` | Постоянный | 10 турниров |
| `veteran_50` | Ветеран | 50 турниров |

### Победы
| Код | Название | Условие |
|---|---|---|
| `first_gold` | Первое золото | выиграть турнир |
| `gold_3` | Трижды первый | выиграть 3 турнира |
| `streak_5` | Серия | 5 побед в матчах подряд, по всем турнирам, в порядке дат |
| `flawless` | Без потерь | выиграть все свои матчи одного турнира |

### Рейтинг
| Код | Название | Условие |
|---|---|---|
| `jump_100` | Рывок | +100 рейтинга за один турнир |
| `level_up` | Новый уровень | подняться на уровень выше прежнего максимума |

### Кругозор
| Код | Название | Условие |
|---|---|---|
| `formats_5` | Многоборец | сыграть 5 разных форматов |
| `formats_all` | Знаток форматов | сыграть все 10 форматов |
| `clubs_3` | Тур по клубам | турниры в 3 разных клубах |

### Вместе
| Код | Название | Условие |
|---|---|---|
| `duo_10` | Сыгранный дуэт | 10 матчей с одним и тем же партнёром |

**Что сознательно не вошло.** «Обыграть пару сильнее на 300 рейтинга» — рейтинг соперника на момент матча нигде не хранится, а считать по сегодняшнему значит врать игроку. Вернуть можно, если начать писать рейтинги участников в момент матча, но это отдельная задача.

## Откуда берутся данные

Новых данных собирать не нужно — всё уже есть.

**`MobileMatchController::getAllMatches($user)`** обходит все десять форматов и по каждому завершённому матчу знает партнёра (id, имя, аватар), обоих соперников, счёт, результат (`win`/`loss`/`draw`), турнир и дату. Этого хватает для победных серий, дуэтов, форматов и «без потерь».

Метод приватный и отдаёт наружу обрезанный вид, поэтому его надо вынести в сервис `PlayerMatchHistory`, которым будут пользоваться и эндпоинт истории матчей, и достижения. При выносе в записи матча добавляются три поля, которых сейчас нет в ответе, а внутри они доступны: `tournament_id`, `tournament_type` и `club_id`.

Без них три значка посчитать нельзя:

- **«Без потерь»** нужен `tournament_id` — сейчас наружу отдаётся только `tournament_name`, а имена турниров повторяются.
- **«Многоборец» и «Знаток форматов»** нужен `tournament_type`. Существующее поле `format` для этого не годится: оно смешивает форматы со стадиями — классические и командные турниры приходят как `group` и `playoff`, а не как `classic` и `team`. Считать форматы по нему значит считать неправильно.
- **«Тур по клубам»** нужен `club_id` — по названию клуба считать нельзя, названия меняются.

**`rating_history`** — на каждое изменение: `rating_before`, `rating_after`, `change`, `tournament_id`, дата. Отсюда «Рывок» и «Новый уровень» (уровень = `floor(rating / 250) * 0.25`, зажат в 1.0…5.75 — см. `RatingCalculator::updateLevel()`).

**`User::getTournamentStats()`** — сколько турниров сыграно и сколько выиграно, с разбивкой по типам.

**Турниры игрока** дают клубы для «Тура по клубам».

## Устройство

### Снимок истории

`PlayerHistory` — одна структура, которую собирают один раз и передают всем правилам: матчи (из `PlayerMatchHistory`), записи рейтинга, статистика турниров, список турниров с клубами.

Это ключевое решение. Без него пятнадцать значков означают пятнадцать проходов по десяти таблицам форматов на каждого игрока — на пересчёте после турнира на 24 человека это 360 обходов.

### Правила

`app/Achievements/` — по классу на значок, все реализуют один интерфейс:

```php
interface Achievement
{
    public function code(): string;        // 'streak_5'
    public function title(): string;       // 'Серия'
    public function description(): string; // 'Пять побед подряд'
    public function icon(): string;        // имя иконки для приложения
    public function group(): string;       // 'wins'
    public function target(): int;         // 5
    public function progress(PlayerHistory $history): int;
}
```

Значок получен, когда `progress >= target`. Прогресс никогда не убывает: раз выданное достижение не отбирается, даже если правило потом поменяют.

Правила живут в коде, а не строками в базе, потому что условия вроде «пять побед подряд» или «все матчи одного турнира выиграны» — это логика, а не число в колонке. Хранить её в базе значило бы писать интерпретатор.

Реестр `AchievementRegistry` перечисляет все правила в порядке показа. Добавить значок = добавить класс и строку в реестр.

### Хранение

Одна таблица `user_achievements`:

| Колонка | Тип | Смысл |
|---|---|---|
| `user_id` | FK users | игрок |
| `code` | string | код значка |
| `progress` | int | текущее значение |
| `target` | int | сколько нужно, снимком на момент выдачи |
| `unlocked_at` | timestamp nullable | когда получен; null — ещё в прогрессе |
| `notified_at` | timestamp nullable | когда ушёл пуш; защита от повторов |

Уникальный индекс `(user_id, code)`, индекс по `user_id`.

`target` хранится снимком, чтобы прогресс в старом пуше и на экране не разъезжался, если порог потом поправят.

Определения значков в базе не дублируются: название и иконка приходят из класса. Награды от клуба, когда до них дойдёт дело, лягут отдельной таблицей `achievement_rewards` с ключом по `code` — переделывать `user_achievements` не придётся.

### Когда пересчитывается

**Экран достижений** — на лету для этого игрока: собрали `PlayerHistory`, прогнали правила, записали в `user_achievements`, отдали. Игрок всегда видит честное состояние. Нагрузка та же, что у существующей истории матчей, которая так и работает.

**Пуши** — командой `achievements:sync` по расписанию раз в десять минут. Команда берёт игроков, у кого за последний час завершились турниры, игры или поединки, пересчитывает их и шлёт пуш по значкам, у которых `unlocked_at` заполнен, а `notified_at` пуст.

Пуши шлёт только команда. Экран пересчитывает молча — иначе открытие профиля порождало бы уведомление о том, что игрок и так видит на экране.

**Чужая карточка** — только чтение `user_achievements`, без пересчёта. Чужой профиль открывают часто, а его достижения обновит либо крон, либо сам владелец.

### API

| Метод | Путь | Отдаёт |
|---|---|---|
| GET | `/api/mobile/achievements` | свои значки: полученные и в прогрессе, с `progress`/`target`, сгруппированные |
| GET | `/api/mobile/players/{user}/achievements` | чужие: только полученные |

Ответ каждого значка: `code`, `title`, `description`, `icon`, `group`, `progress`, `target`, `unlocked_at`.

### Уведомления

Новая категория `achievement` добавляется в список в `MobileNotificationController::categories()` (сейчас там пять: tournament, booking, challenge, support, general) и в локализации приложения — ru, en, kk.

Запись в `notifications`: `type = 'achievement'`, `category = 'achievement'`, в `data` — `achievement_code`, чтобы приложение открыло нужный экран.

### Приложение

- `lib/widgets/profile/achievements_section.dart` — виджет уже написан, но показывает четыре выдуманных значка и нигде не подключён. Переводим на реальные данные и включаем в профиль.
- Новый экран со всеми значками по группам.
- Блок полученных значков на `player_profile_screen.dart`.
- `AchievementService` + модель `Achievement` рядом с остальными сервисами.
- Обработка пуша `type = 'achievement'` в `push_notification_service.dart` — открыть экран достижений.

Экран и виджет читают одно и то же представление, поэтому вёрстка значка — один переиспользуемый элемент.

## Запуск

На релизе у каждого игрока разом «откроется» вся его история: у активных наберётся по десять значков и больше. Если крон отработает честно, человек получит пуш за то, что заработал полгода назад. Это читается как спам и обесценивает механику с первого дня.

Поэтому релиз идёт молча. Одноразовая команда `achievements:backfill` при деплое проходит по всем игрокам, считает прогресс и проставляет уже полученным значкам `notified_at` задним числом. Пуши начинают уходить только за то, что заработано после релиза. Игрок открывает профиль и обнаруживает, что у него уже семь значков, — без единого уведомления.

**Выключатель рассылки.** `ACHIEVEMENTS_PUSH_ENABLED` в `.env`, по умолчанию выключен. Пока выключен, крон считает значки, но молчит — это нужно, чтобы серверную часть можно было выкатить раньше релиза приложения. В старой сборке экрана значков нет: тап по пушу «Новое достижение» не открыл бы ничего.

Важная деталь: при выключенной рассылке `notified_at` всё равно проставляется. Иначе в день включения на игроков разом высыпалось бы всё, что накопилось за тихий период, — ровно то, от чего спасает заливка истории.

**Команда заливки физически не умеет слать пуши.** Не флаг `--no-push`, который можно забыть, а отсутствие самой возможности: заливка и рассылка — разные классы, у заливки нет доступа к отправке.

Это важнее, чем кажется. `FCMNotificationService::sendToUser()` шлёт напрямую, без фильтра тестовых номеров — `PUSH_TEST_PHONES` работает только внутри `TournamentPushService` и достижения не прикроет. Ошибка в заливке означала бы рассылку на всю базу, и остановить её было бы нечем.

Команда идёт пачками по игрокам и логирует прогресс: на боевой базе это долгий проход по десяти таблицам форматов. Повторный запуск безопасен — прогресс перезаписывается, `notified_at` у уже отмеченных не трогается.

Игроки, зарегистрировавшиеся после заливки, проходят обычным путём: у них нет записей, первые значки для них честно новые, пуш уместен.

## Ошибки и крайние случаи

**У игрока нет ни одного матча.** Экран показывает все значки в прогрессе с нулём. Пустого состояния нет — это и есть список целей.

**Пересчёт упал на одном игроке.** Команда логирует и идёт дальше: один сломанный профиль не должен ронять рассылку остальным.

**Пуш не ушёл.** `notified_at` всё равно проставляется, повтора не будет. Запись в `notifications` создаётся до отправки, так что значок виден в приложении в любом случае. Повторять попытку нельзя: чаще всего «не ушёл» означает, что у игрока просто не установлено приложение, и крон бесконечно плодил бы уведомления каждые десять минут.

**Игрок получил пять значков разом** (первый турнир закрывает «Дебют», «Первую победу», «Многоборца»). Шлём один пуш: «Новых достижений: 3», без перечисления. Пять уведомлений подряд — это спам.

**Порог значка изменили задним числом.** Уже выданные не отбираются: `unlocked_at` остаётся, `target` у них хранится снимком.

**Матч отредактировали после турнира.** Следующий пересчёт учтёт правку. Значок, полученный по старому счёту, остаётся — отбирать награду за чужую ошибку нельзя.

## Проверка

**На правила** — по тесту на значок, на готовой истории игрока. Отдельно: серия прерывается любым не-выигрышем, включая ничью; «без потерь» не засчитывается, если в турнире была ничья; дуэт считает партнёра, а не соперника; форматы считаются по типу турнира, а классический турнир не превращается в два формата из-за групп и плей-офф.

**На снимок истории** — `PlayerHistory` собирается за один проход, матчи всех десяти форматов попадают внутрь, у каждого проставлены `tournament_id`, `tournament_type` и `club_id`.

**На вынос `PlayerMatchHistory`** — существующий эндпоинт `/api/mobile/matches/history` после рефакторинга отдаёт ровно то же, что и раньше: набор полей, порядок сортировки и пагинация не меняются.

**На выдачу** — прогресс растёт, `unlocked_at` ставится один раз, повторный пересчёт не плодит записей и не шлёт второй пуш.

**На команду синхронизации** — берёт только игроков недавних турниров, шлёт один пуш на пачку значков, падение на одном игроке не останавливает остальных.

**На заливку** — проставляет `notified_at` всем уже полученным значкам, не отправляет ни одного пуша, повторный запуск не ломает данные и не будит уведомления. Отдельным тестом: после заливки команда синхронизации молчит по историческим значкам и срабатывает по новому.

**На API** — свои значки отдаются с прогрессом, чужие только полученные, чужой профиль не пересчитывается.
