# Привязка брони корта к турниру

**Дата:** 7 августа 2026
**Статус:** согласовано, готово к планированию

## Задача

На `/club/courts/schedule` при бронировании слота есть тип брони «Турнир», но за кнопкой ничего не стоит: `booking_type` просто записывается в БД. Нужно дать выбор конкретного турнира из `/club/tournaments` и считать цену брони от данных турнира.

Формула: **цена турнира × число оплативших участников**. Если у турнира цена 20 000 ₸ и 5 оплативших участников, бронь показывает 100 000 ₸.

Работает в трёх местах: создание брони, редактирование брони, недельный вид расписания.

## Решения

| Вопрос | Решение |
|---|---|
| Какие турниры в списке | Открытые и идущие (`status` = `open`, `in_progress`) турниры клуба |
| Пересчёт цены | Живой — при каждом открытии расписания |
| Поля «Клиент» и «Оплата» | Скрываются, как у групповой брони |
| Турнир на нескольких кортах | Сумма делится поровну между бронями |
| База деления | Брони турнира в пределах одной даты |
| Хранение цены | В `court_bookings.price`, как у обычных броней |

### Почему цена хранится, а не считается на лету

`price` читают 13 отчётов, кассовые сводки, экспорт в Excel и мобильное API. Вычисляемый аксессор потребовал бы править все эти места, и любое новое место, забывшее про аксессор, тихо показало бы ноль. Храним посчитанное значение — потребители не меняются.

### Почему колонка, а не отдельная таблица

У групп отдельная таблица `club_group_sessions` оправдана: там своя сущность «занятие» со статусом, тренером и посещаемостью. У турнира это ссылка 1:1 без собственных данных — колонки достаточно.

«Как в групповом» из постановки относится к UI: тот же выпадающий список, тот же блок участников, та же логика скрытия полей. Это повторяется один в один.

## Архитектура

### Миграция

`court_bookings.tournament_id` — `nullable`, `foreignId`, `nullOnDelete`. Удаление турнира не трогает брони, они лишь перестают быть турнирными и сохраняют последнюю посчитанную цену.

Индекс `(tournament_id, date)` — по нему сервис собирает набор броней для деления.

### Модели

- `CourtBooking`: `tournament_id` в `$fillable`, связь `tournament()`.
- `Tournament`: связь `courtBookings()` — чтобы видеть, какие корты забронированы за турниром.

### Сервис `app/Services/TournamentBookingPriceService.php`

Единственная зона ответственности — цена турнирных броней.

```php
// Сколько всего должен стоить турнир на эту дату
public function totalForDate(Tournament $t): float
// = (float) $t->price * $t->approvedParticipantsCount()

// Разложить сумму по броням турнира на дату; true, если что-то изменилось
public function syncForDate(Tournament $t, string $date): bool
```

`syncForDate` берёт брони турнира за дату со `status = 'confirmed'` (отменённые, `cancelled`, не участвуют), делит `totalForDate` на их количество и записывает `price` каждой. Остаток от деления кладётся в первую по времени бронь, чтобы сумма сходилась точно.

Если броней за дату нет, метод ничего не делает и возвращает `false`.

Число участников берётся из готового `Tournament::approvedParticipantsCount()` (`app/Models/Tournament.php:626`) — он уже различает личные турниры (статус `registered`) и командные (`approved`-пары × 2). Своей логики подсчёта сервис не содержит.

### Точки вызова

- `CourtController::schedule` и `CourtController::scheduleWeek` — для турниров в видимом диапазоне дат. Это и есть живой пересчёт.
- После создания, редактирования и отмены турнирной брони.
- При смене турнира у брони или снятии типа «Турнир» пересчитываются **оба** набора — старый и новый.

Скидка и `custom_price` для турнирной брони обнуляются — как сделано для групповой (`CourtController.php:848`).

## UI

### Модалка создания (`schedule.blade.php`)

Блок `bookTournamentSelectWrap` — копия структуры `bookGroupSelectWrap` (`:713`):

- `<select name="tournament_id">` с названием и датой турнира: «Американо 08.08»;
- строка расчёта: «5 оплативших × 20 000 = 100 000 ₸», второй строкой при нескольких кортах — «делится на 4 корта → 25 000 ₸ за этот корт»;
- блок участников со списком оплативших — вёрстка `groupMembersBlock`;
- ссылка «Открыть турнир» на `/club/tournaments/{id}`.

Данные приходят одним JSON `window.__tournaments` (id → цена, число оплативших, имена участников, число уже существующих турнирных броней по датам).

Пересчёт в модалке идёт на клиенте, без запроса. **Делитель в предпросмотре — существующие брони турнира на выбранную дату плюс создаваемая.** То есть если корт для турнира бронируют первым, показывается вся сумма; если у турнира на эту дату уже есть 3 брони — показывается сумма, делённая на 4.

JS: в `selectBookingType` (`:2226`) добавляется ветка `isTournament` рядом с `isGroup`; функция `renderTournamentInfo(tournamentId)` — сестра `renderGroupMembers` (`:2257`).

Классы скрытия полей обобщаются: `.js-hide-for-group` дополняется `.js-hide-for-tournament`. Существующий класс не переименовывается, чтобы не тащить правки по всему файлу.

### Модалка редактирования

Блок `editTournamentBlock`, функция `applyEditTournamentVisibility` параллельно `applyEditGroupVisibility` (`:2348`). Контроллер отдаёт `bookingTournamentIds` — карту `booking_id → tournament_id`, как уже отдаёт `bookingGroupIds` (`CourtController.php:149`). Турнир открытой брони подставляется в селект, его можно сменить или отвязать.

### Недельный вид (`schedule_week.blade.php`)

Те же блоки и тот же JSON. Контроллер готовит данные для обоих видов одинаково (`:137` и `:344`) — турниры добавляются туда же. Слот красится существующим `.bt-slot-tournament` (`:4009`), цена в плитке уже поделённая.

## Краевые случаи

| Ситуация | Поведение |
|---|---|
| Турнир выбран, оплативших нет | Цена 0 ₸, подпись «оплативших пока нет — цена появится после записи» |
| У турнира не задана `price` | Цена 0 ₸, подсказка со ссылкой «укажите цену в турнире» |
| Участник добавился после брони | При следующем открытии расписания цена вырастет |
| Турнир удалён | `tournament_id` обнуляется, бронь сохраняет последнюю цену |
| Бронь отменена | Выпадает из делителя, остальные брони дорожают при следующем открытии |
| Повтор брони на другие даты | Каждая дата считается своим набором |

## Тестирование

Фича-тест на `TournamentBookingPriceService`:

- 5 оплативших × 20 000 на одном корте → 100 000;
- те же данные на четырёх кортах → по 25 000;
- деление на три корта не теряет остаток (33 333 / 33 333 / 33 334);
- участники в статусе `pending` и `waiting` в расчёт не входят;
- отмена одной из четырёх броней поднимает остальные.

Прогон точечный через `--filter`: в сьюте есть ~14 давно падающих тестов, не связанных с этой работой.

## Вне рамок

- Автосоздание броней кортов при создании турнира.
- Отражение турнирных броней в отчётах отдельной строкой — они попадают в общую выручку по существующей логике `price`.
- Учёт оплаты корта отдельно от взносов за турнир.
